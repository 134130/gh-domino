# gh-domino 3.0.0 Plan

## Release Intent

3.0.0 should turn gh-domino from a single interactive flow into a small
application with multiple adapters:

- TUI by default for `gh domino`
- CLI subcommands for scriptable use
- shared domain planning and execution logic
- git/gh command execution through gitkit
- higher-fidelity integration tests backed by local Git and fake GitHub PR state

The main architectural goal is to keep the domain behavior independent from the
presentation mode. CLI and TUI should ask the same application service for a
plan, then choose how to display, filter, confirm, and execute it.

## Proposed Command Surface

Default:

```console
gh domino
```

Starts the TUI.

List:

```console
gh domino list [--all] [--broken] [--json]
```

Builds the stack graph and prints the current state without mutating anything.

Merge:

```console
gh domino merge [--dry-run] [--yes] [--all] [--pr <number>...] [--subtree <number>...] [--chain <number>...] [--json]
```

Executes the same repair/update actions that the TUI confirms interactively.
`--dry-run` prints the action plan. `--yes` runs without prompts.

Open naming question: `merge` matches the user-facing workflow, but the command
does not merge PRs directly. Internally this action should be named repair,
sync, or execute to avoid leaking misleading terminology into the domain layer.

## Package Boundaries

Target package shape:

- `internal/app`: application service, command use cases, dependency injection
- `internal/domino`: domain model and planning logic
- `internal/cli`: command parsing, CLI output formatting, exit behavior
- `internal/tui`: Bubble Tea views only
- `internal/output`: terminal/JSON rendering helpers
- `gitobj`: GitHub data types, until replaced by a gitkit/gh package boundary

The current `internal/domino.Run` should be split into:

- load current repository and PR state
- build stack graph
- compute PR statuses and action plan
- execute selected actions
- render plan/results

This removes the current coupling between state calculation, spinners, prompts,
TUI selection, and git command execution.

## gitkit Migration

Use gitkit as the command boundary:

- replace the global `git.CommandRunner` with injected `gitcmd.Runner`
- replace `git.CommandModifier` with `gitcmd.Command`/`gitcmd.Client` usage
- use `gitrepo.Client` for local repository operations
- use `ghcli.Client` for low-level GitHub CLI operations
- use `ghpr` for merge strategy semantics where possible

Keep a temporary adapter if needed:

```go
type Services struct {
    Git  gitrepo.Client
    GH   ghcli.Client
    PR   ghpr.Client
    Run  gitcmd.Runner
}
```

Tests should inject a fake `gitcmd.Runner` rather than mutating package globals.

## Integration Test Strategy

Use focused command-runner tests for store/executor boundaries, then use
`test/harness` for end-to-end scenarios.

The default integration harness should:

- create a real local Git repository/worktree fixture
- seed fake GitHub PR metadata in memory
- delegate Git operations to real `git`
- fake only the narrow `gh pr` mutations the executor uses
- assert mutating `merge --yes` behavior through local Git refs and fake PR state

Do not use `vercel-labs/emulate` in the default suite. A real GitHub smoke test
can be added later behind an explicit tag if the project needs API compatibility
coverage beyond the fake PR state.

## TUI Rewrite

The TUI should be rewritten against the new application service rather than
patched in place.

Expected feature set:

- load state with clear progress and error states
- show stack tree and PR status
- filter all/broken/selected
- select/deselect PRs
- preview pending actions before execution
- execute with per-action progress and final result summary
- avoid embedding business decisions in Bubble Tea update/view code

The first TUI milestone should optimize for correctness and stable layout over
visual richness.

## Stability Work

Areas to harden before 3.0.0:

- no package-level mutable runner or output writer
- context cancellation consistently aborts command execution
- rebase conflict cleanup is deterministic
- worktree paths are unique and sanitized
- concurrent stack processing has bounded parallelism and structured results
- branch/base updates are idempotent where possible
- dry-run and real execution share the same action plan
- JSON output is stable enough for automation

## Migration Order

1. Introduce app/domain planning types.
2. Add CLI command parser for the v3 command model.
3. Move read-only `list`, `plan`, and `merge --dry-run` onto the app service.
4. Add gitkit dependency and replace the old git runner behind the service.
5. Add `test/harness` scenario test scaffolding.
6. Rebuild TUI on top of the app service.
7. Move mutating `merge` execution to the new executor.
8. Remove old global runner paths and old TUI flow.
9. Update README and release notes for 3.0.0.
