# gh-domino 3.0.0 CLI Design

## Current Core Capabilities

Current gh-domino mainly supports five user-facing capabilities:

1. Discover stacked PRs
   - fetch `origin`
   - list open PRs authored by the current user
   - list recently merged PRs authored by the current user
   - build a dependency tree from `baseRefName` and `headRefName`

2. Detect broken PRs
   - base branch belongs to a PR that has already been merged
   - parent branch in a stack has diverged from the child PR
   - root PR still contains commits from a recently merged PR
   - merge strategy handling currently covers merge commit, squash merge, and
     rebase merge through Git ancestry checks

3. Preview repairs
   - print the dependency tree
   - print which PRs would be rebased
   - print whether a PR base branch would be updated

4. Repair broken PRs
   - rebase the branch onto the correct new base
   - use `--onto` when squash-merge repair needs an upstream commit
   - abort rebase on conflict
   - force push with lease
   - update the GitHub PR base branch when needed

5. Update clean PRs on demand
   - call `gh pr update-branch --rebase`
   - currently exposed through `--rebase-all` and TUI selection of non-broken PRs

The current default interactive mode also supports selecting PRs and processing
independent stacks in parallel using temporary Git worktrees.

## CLI Principles

- Commands should describe user intent, not implementation details.
- Dry-run and real execution must be based on the same action plan.
- TUI and CLI should consume the same `Plan`.
- Human output can be compact, but JSON output must be stable.
- Mutating commands should require either confirmation or `--yes`.
- Existing flags should keep working during the 3.0.0 transition.

## Command Tree

```text
gh domino [flags]                 # default TUI
gh domino tui [flags]             # explicit TUI
gh domino list [flags]            # inspect stacks and statuses
gh domino plan [flags]            # show executable action plan
gh domino merge [flags]           # execute selected actions
```

`plan` is intentionally separate from `list`:

- `list` answers "what PR stacks exist and what state are they in?"
- `plan` answers "what would gh-domino do?"
- `merge` answers "run that plan."

If we want fewer commands, `merge --dry-run` can cover `plan`, but keeping
`plan` makes the CLI clearer and gives automation a non-mutating command with a
stable contract.

## Global Flags

Available on all commands:

```text
--repo <owner/name>      GitHub repository override
--remote <name>          Git remote to fetch and inspect (default: origin)
--author <login>         PR author filter (default: @me)
--merged-limit <n>       recently merged PR lookup limit (default: 30)
--format <format>        human|json (default: human)
--no-color               disable ANSI color
--verbose                print command/progress details
```

Notes:

- `--repo` should be passed to `gh` commands, but local Git still needs a
  working tree unless the command is explicitly made remote-only later.
- `--format json` is preferred over `--json` because future formats can be added
  without more boolean flags.
- Keep `--json` as a hidden alias for `--format json` if useful.

## `gh domino`

```text
gh domino
```

Default behavior:

- starts the TUI
- loads the same plan as `gh domino plan`
- allows selecting actions interactively
- executes selected actions after confirmation

Compatibility:

```text
gh domino --dry-run      -> gh domino plan
gh domino --auto         -> gh domino merge --yes
gh domino --headless     -> hidden/test mode during migration
gh domino --rebase-all   -> gh domino merge --yes --include-clean
```

## `gh domino tui`

```text
gh domino tui [--include-clean]
```

Runs the explicit TUI mode.

Flags:

```text
--include-clean          allow update-branch actions for clean PRs
```

The TUI should not expose every CLI filter initially. It should start with a
small set and keep selection/filtering inside the interface.

## `gh domino list`

```text
gh domino list [--state <state>] [--stack <pr>] [--format human|json]
```

Shows PRs and stack state. It does not show every executable step.

Flags:

```text
--state <state>          all|broken|clean|updateable (default: all)
--stack <pr-number>      show only the stack containing a PR
--flat                   print rows instead of a tree
```

Human output:

```text
Pull Requests
└─ #52 bar (stack-1 <- stack-2) [broken: merged_base -> main]
   └─ #53 baz (stack-2 <- stack-3) [broken: parent_diverged]
```

JSON output shape:

```json
{
  "repository": "owner/repo",
  "pulls": [
    {
      "number": 52,
      "title": "bar",
      "base": "stack-1",
      "head": "stack-2",
      "state": "broken",
      "reason": "merged_base",
      "newBase": "main",
      "upstream": "abc123"
    }
  ]
}
```

## `gh domino plan`

```text
gh domino plan [--include-clean] [--pr <number>] [--format human|json]
```

Builds and prints the action plan. This is the preferred scriptable dry-run
command.

Flags:

```text
--include-clean          include update-branch actions for clean PRs
--pr <number>            plan only actions for this PR
--stack <number>         plan actions for the stack containing this PR
```

Human output:

```text
Actions
  repair #52 stack-2 onto main (upstream abc123)
  repair #53 stack-3 onto stack-2
```

JSON output shape:

```json
{
  "actions": [
    {
      "id": "repair-pr-52",
      "kind": "repair_pr",
      "pr": 52,
      "head": "stack-2",
      "newBase": "main",
      "upstream": "abc123",
      "dependsOn": []
    }
  ]
}
```

## `gh domino merge`

```text
gh domino merge [--yes] [--dry-run] [--include-clean] [--pr <number>]
```

Executes the action plan.

Flags:

```text
--yes                   run without interactive confirmation
--dry-run               alias for gh domino plan
--include-clean         include update-branch actions for clean PRs
--pr <number>           execute only actions for this PR
--stack <number>        execute actions for the stack containing this PR
--parallel <n>          max independent stacks to process in parallel (default: 1 CLI, auto TUI later)
--worktree-dir <path>   temp worktree base directory
```

Behavior:

- without `--yes`, print the plan and ask for confirmation
- with `--dry-run`, never mutate and use `plan` behavior
- process actions in dependency order
- independent stacks may be processed in parallel only when `--parallel > 1`
- on rebase conflict, abort rebase, report manual command, and continue or stop
  according to a later `--continue-on-error` option

Initial recommendation: default `--parallel 1` for CLI. Parallelism is useful,
but deterministic output and failure handling matter more for the first CLI
contract.

## Exit Codes

```text
0   success, no action needed is also success
1   execution or validation error
2   invalid CLI usage
3   user cancelled
4   rebase conflict
```

For `merge`, rebase conflict should be distinguishable from generic failure so
automation can stop and ask for manual resolution.

## Naming Decisions

Recommended user-facing names:

- `list`: current repository stack state
- `plan`: exact action preview
- `merge`: repair after a merge

Rejected or deferred:

- `repair`: technically accurate, but less connected to the user's trigger
- `sync`: too vague
- `rebase`: too narrow because the command can also update PR base and run
  update-branch
- `run`: too generic

Internally, use `Repair` or `Execute`, not `Merge`, because gh-domino does not
merge PRs.
