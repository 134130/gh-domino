# gh-domino 3.0.0 CLI Design

## Current Core Capabilities

Current gh-domino mainly supports five user-facing capabilities:

1. Discover stacked PRs
   - fetch `origin`
   - list open PRs authored by the current user
   - list recently merged PRs authored by the current user
   - build a dependency tree from `baseRefName` and `headRefName`

2. Detect broken PRs
   - base branch belongs to a PR that has already been merged
   - parent branch in a stack has diverged from the child PR
   - root PR still contains commits from a recently merged PR
   - merge strategy handling currently covers merge commit, squash merge, and
     rebase merge through Git ancestry checks

3. Preview repairs
   - print the dependency tree
   - print which PRs would be rebased
   - print whether a PR base branch would be updated

4. Repair broken PRs
   - rebase the branch onto the correct new base
   - use `--onto` when squash-merge repair needs an upstream commit
   - abort rebase on conflict
   - force push with lease
   - update the GitHub PR base branch when needed

5. Update clean PRs on demand
   - call `gh pr update-branch --rebase`
   - v3 should expose this as `--include-clean`

The current default interactive mode also supports selecting PRs and processing
independent stacks in parallel using temporary Git worktrees.

## CLI Principles

- Commands should describe user intent, not implementation details.
- Dry-run and real execution must be based on the same action plan.
- TUI and CLI should consume the same `Plan`.
- Human output can be compact, but JSON output must be stable.
- Mutating commands should require either confirmation or `--yes`.
- Existing flags should keep working during the 3.0.0 transition.

## Command Tree

```text
gh domino [flags]                 # default TUI
gh domino tui [flags]             # explicit TUI
gh domino list [flags]            # inspect stacks and statuses
gh domino plan [flags]            # show executable action plan
gh domino merge [flags]           # execute selected actions
```

`plan` is intentionally separate from `list`:

- `list` answers "what PR stacks exist and what state are they in?"
- `plan` answers "what would gh-domino do?"
- `merge` answers "run that plan."

If we want fewer commands, `merge --dry-run` can cover `plan`, but keeping
`plan` makes the CLI clearer and gives automation a non-mutating command with a
stable contract.

## Global Flags

Available on all commands:

```text
--repo <owner/name>      GitHub repository override
--remote <name>          Git remote to fetch and inspect (default: origin)
--author <login>         PR author filter (default: @me)
--merged-limit <n>       recently merged PR lookup limit (default: 30)
--format <format>        human|json (default: human)
--no-color               disable ANSI color
--verbose                print command/progress details
```

Notes:

- `--repo` should be passed to `gh` commands, but local Git still needs a
  working tree unless the command is explicitly made remote-only later.
- `--format json` is preferred over `--json` because future formats can be added
  without more boolean flags.

## `gh domino`

```text
gh domino
```

Default behavior:

- starts the TUI
- loads the same plan as `gh domino plan`
- allows selecting actions interactively
- executes selected actions after confirmation

## `gh domino tui`

```text
gh domino tui [--include-clean]
```

Runs the explicit TUI mode.

Flags:

```text
--include-clean          allow update-branch actions for clean PRs
```

The TUI should not expose every CLI filter initially. It should start with a
small set and keep selection/filtering inside the interface.

## `gh domino list`

```text
gh domino list [--state <state>] [--format human|json]
```

Shows PRs and stack state. It does not show every executable step.

Flags:

```text
--state <state>          all|broken|clean|updateable (default: all)
--flat                   print rows instead of a tree
```

Human output:

```text
Pull Requests
└─ #52 bar (stack-1 <- stack-2) [broken: merged_base -> main]
   └─ #53 baz (stack-2 <- stack-3) [broken: parent_diverged]
```

JSON output shape:

```json
{
  "repository": "owner/repo",
  "pulls": [
    {
      "number": 52,
      "title": "bar",
      "base": "stack-1",
      "head": "stack-2",
      "state": "broken",
      "reason": "merged_base",
      "newBase": "main",
      "upstream": "abc123"
    }
  ]
}
```

## `gh domino plan`

```text
gh domino plan [--include-clean] [--pr <number>...] [--subtree <number>...] [--chain <number>...] [--format human|json]
```

Builds and prints the action plan. This is the preferred scriptable dry-run
command.

Flags:

```text
--include-clean          include update-branch actions for clean PRs
--pr <number>            plan actions targeting exactly this PR; repeatable
--subtree <number>       plan actions for this PR and its descendants; repeatable
--chain <number>         plan actions for the root-to-PR ancestor chain; repeatable
```

Human output:

```text
Actions
  repair #52 stack-2 onto main (upstream abc123)
  repair #53 stack-3 onto stack-2
```

JSON output shape:

```json
{
  "actions": [
    {
      "id": "repair-pr-52",
      "kind": "repair_pr",
      "pr": 52,
      "head": "stack-2",
      "newBase": "main",
      "upstream": "abc123",
      "dependsOn": []
    }
  ],
  "warnings": []
}
```

## `gh domino merge`

```text
gh domino merge [--yes] [--dry-run] [--include-clean] [--pr <number>...] [--subtree <number>...] [--chain <number>...]
```

Executes the action plan.

Flags:

```text
--yes                   run without interactive confirmation
--dry-run               print the selected action plan without mutating
--include-clean         include update-branch actions for clean PRs
--pr <number>           execute actions targeting exactly this PR; repeatable
--subtree <number>      execute actions for this PR and its descendants; repeatable
--chain <number>        execute actions for the root-to-PR ancestor chain; repeatable
--parallel <n>          max independent stacks to process in parallel (default: 1 CLI, auto TUI later)
--worktree-dir <path>   temp worktree base directory
```

Behavior:

- without `--yes`, print the plan and ask for confirmation
- with `--dry-run`, never mutate and use `plan` behavior
- process actions in dependency order
- independent stacks may be processed in parallel only when `--parallel > 1`
- on rebase conflict, abort rebase, report manual command, and continue or stop
  according to a later `--continue-on-error` option

Initial recommendation: default `--parallel 1` for CLI. Parallelism is useful,
but deterministic output and failure handling matter more for the first CLI
contract.

## Selection Semantics

`--pr`, `--subtree`, and `--chain` should support repeated values:

```console
gh domino plan --pr 52 --pr 57
gh domino plan --subtree 52 --chain 80
gh domino merge --yes --chain 52 --chain 80
```

Do not require users to run multiple gh-domino processes for this. gh-domino
needs a single repository snapshot to understand dependencies and avoid
conflicting branch mutations.

Selection should be a union:

- no selector: all actionable PRs
- `--pr`: actions targeting exactly the selected PRs
- `--subtree`: actions targeting selected PRs and their descendants
- `--chain`: actions targeting the root-to-PR ancestor chain
- multiple selector types: union of all selected actions

The selected action set should be deduplicated by action ID.

Selection is explicit. gh-domino should not automatically include parent repair
actions or repair related branches that the user did not select. If a selected
action depends on an unselected action, `plan` should keep the selected action
set unchanged and emit a warning. Users can choose `--chain` for ancestors or
`--subtree` for descendants when they want a larger scope.

Planning still analyzes the whole repository first:

1. load all relevant PRs and refs
2. build the full dependency graph
3. build the full action plan
4. apply selection scope
5. attach warnings for unselected related actions
6. render or execute the selected plan

This separates analysis scope from execution scope.

## Parallelism

Internal parallelism is preferable to external parallel execution.

External parallel execution is risky because each process would:

- run its own fetch/list/plan cycle
- miss other selected actions from sibling processes
- race on local branches and worktrees
- push branches without a shared dependency scheduler
- duplicate GitHub API calls

Internal parallel execution can build one `Plan`, then execute selected actions
with a bounded DAG scheduler:

- actions in the same stack keep dependency order
- only selected dependency edges affect scheduling
- unselected dependencies are warnings, not implicit work
- independent stacks can run concurrently
- each mutating branch action gets its own worktree
- `--parallel <n>` limits concurrency
- output and results stay coordinated in one process

The first implementation can keep `--parallel 1` while the action/result model
is stabilized. After the executor has structured results, increase the default
for TUI or add an `auto` mode if needed.

## Exit Codes

```text
0   success, no action needed is also success
1   execution or validation error
2   invalid CLI usage
3   user cancelled
4   rebase conflict
```

For `merge`, rebase conflict should be distinguishable from generic failure so
automation can stop and ask for manual resolution.

## Naming Decisions

Recommended user-facing names:

- `list`: current repository stack state
- `plan`: exact action preview
- `merge`: repair after a merge

Rejected or deferred:

- `repair`: technically accurate, but less connected to the user's trigger
- `sync`: too vague
- `rebase`: too narrow because the command can also update PR base and run
  update-branch
- `run`: too generic

Internally, use `Repair` or `Execute`, not `Merge`, because gh-domino does not
merge PRs.

## M2-2 Output Contract

The current M2 implementation routes the read-only command contract:

- `gh domino list`
- `gh domino plan`
- `gh domino merge --dry-run`

The next CLI milestone should not add more command names. It should stabilize
the contract of the commands that now exist.

### Contract To Freeze First

Freeze these outputs with tests:

```text
gh domino list
gh domino list --flat
gh domino list --state broken
gh domino list --format json
gh domino plan
gh domino plan --include-clean
gh domino plan --pr 52
gh domino plan --subtree 52
gh domino plan --chain 52
gh domino plan --format json
gh domino merge --dry-run
```

The JSON contract should use lowerCamelCase and omit empty optional fields.

`list --format json` should eventually include repository metadata:

```json
{
  "repository": {
    "nameWithOwner": "owner/repo",
    "remote": "origin"
  },
  "pulls": []
}
```

But this should wait until the store can reliably expose repository identity.
Until then, keeping only `pulls` is acceptable as a transitional contract.

`plan --format json` should be treated as the first stable automation surface:

```json
{
  "actions": [
    {
      "id": "repair-pr-52",
      "kind": "repair_pr",
      "pr": 52,
      "head": "stack-2",
      "newBase": "main",
      "upstream": "abc123",
      "reason": "merged_base",
      "dependsOn": ["repair-pr-51"]
    }
  ],
  "warnings": [
    {
      "kind": "unselected_dependency",
      "pr": 53,
      "actionId": "repair-pr-53",
      "dependencyId": "repair-pr-52",
      "dependencyPr": 52,
      "dependencyKind": "repair_pr",
      "dependencyHead": "stack-2",
      "dependencyBase": "main",
      "dependencyReason": "merged_base"
    }
  ]
}
```

### Filters

Implement filters in this order:

1. `--state` for `list`
2. repeatable `--pr` for `plan` and `merge --dry-run`
3. repeatable `--subtree` for `plan` and `merge --dry-run`
4. repeatable `--chain` for `plan` and `merge --dry-run`

`--pr` should select only target PR actions. It should not automatically include
dependency actions.

`--subtree` should select target PR actions and all descendant PR actions. This
matches the TUI behavior of selecting a node and its child tree.

`--chain` should select actions on the selected PR's root-to-PR ancestor path.
It should not select descendants or sibling branches. Users who want a whole
tree should select the root PR with `--subtree`.

### Exit Behavior

Before adding execution through the new app executor, introduce a small exit
classifier in `internal/cli`:

```go
type ExitError struct {
    Code int
    Err  error
}
```

This lets invalid usage become exit code `2` without relying on string matching
in `main`.
