# gh-domino 3.0.0 Design

## Design Goal

3.0.0 should make gh-domino usable in two modes without duplicating behavior:

- a default TUI mode for interactive branch repair
- explicit CLI subcommands for automation and reproducible output

Both modes must share the same planning and execution engine. The TUI should not
decide whether a PR is broken. The CLI should not have its own dry-run logic.
They should both consume a domain-level `Plan`.

## Current Problems

The current code works, but the boundaries are too implicit:

- `internal/domino.Run` performs config routing, loading, planning, rendering,
  prompting, mutation, and result reporting.
- `git.CommandRunner` and `write` are package-level mutable globals.
- dry-run mutates `prHeadShas` with `"dummy-sha-after-rebase"` to model later
  actions.
- TUI state calculation duplicates parts of the headless flow.
- `git.CommandModifier` exposes `*exec.Cmd`, so execution details leak through
  the codebase.
- integration tests replay YAML command logs, which is fast but cannot validate
  actual Git repository state transitions.

3.0.0 should treat the implementation as a greenfield boundary. It should
preserve the core workflow, but it does not need compatibility aliases or
parallel legacy execution paths.

## User-Facing Commands

### Default

```console
gh domino
```

Runs the TUI. This is equivalent to:

```console
gh domino tui
```

The explicit `tui` command can exist but does not need to be documented heavily.

### List

```console
gh domino list [--all] [--broken] [--json]
```

Loads repository state and prints the current stack graph and PR status. It never
mutates local Git state or GitHub state.

Suggested semantics:

- default: show all open stacked PRs with status
- `--broken`: show only PRs with planned repair actions
- `--all`: include non-stacked open PRs if the loader can identify them
- `--json`: emit the stable `Plan` JSON shape

### Merge

```console
gh domino merge [--dry-run] [--yes] [--all] [--pr <number>] [--subtree <number>] [--stack <number>] [--json]
```

The name is user-facing: the user has merged something and wants the rest of the
stack fixed. Internally this should be called `repair`, `sync`, or `execute`.

Suggested semantics:

- default: build a plan and ask before mutating
- `--dry-run`: print the exact actions that would run
- `--yes`: run without prompts
- `--all`: include update-branch actions for non-broken PRs
- `--pr`: restrict the action plan to exactly selected PR actions
- `--subtree`: restrict the action plan to selected PRs and descendants
- `--stack`: restrict the action plan to the root stack containing selected PRs
- `--json`: emit action/result JSON instead of human terminal output

## Architecture

Target dependency direction:

```text
cmd/gh-domino
  -> internal/cli
      -> internal/app
          -> internal/domino
          -> internal/stackedpr
          -> gitkit packages
  -> internal/tui
      -> internal/app
          -> internal/domino
```

`internal/app` is the composition layer. It owns dependency injection and use
cases. `internal/domino` owns domain decisions. CLI and TUI are adapters.

## Package Responsibilities

### `internal/cli`

Responsibilities:

- parse command names and flags
- configure output mode
- translate process errors into exit codes

It should not call `git` or `gh` directly.

### `internal/app`

Responsibilities:

- load repository state
- ask the domain package for a plan
- apply selection/filter options
- execute actions
- return structured results

Proposed public surface:

```go
type App struct {
    store    RepositoryStore
    planner  Planner
    executor Executor
}

func (a App) BuildPlan(ctx context.Context, opts PlanOptions) (*Plan, error)
func (a App) Execute(ctx context.Context, plan *Plan, opts ExecuteOptions) (*RunResult, error)
```

The app layer is the first place where `gitkit` clients should appear. Domain
types should not know how commands are executed.

### `internal/domino`

Responsibilities:

- classify PR state
- choose repair actions
- preserve action ordering
- model dry-run and real execution the same way

It should not print, prompt, start spinners, create Bubble Tea commands, or call
`git`/`gh`.

### `internal/tui`

Responsibilities:

- render loading, plan, selection, confirmation, execution progress, and result
  screens
- own keyboard interactions
- ask `internal/app` for plan and execution results

The TUI can select actions, but it should not compute actions.

### `internal/output`

Responsibilities:

- render human terminal output
- render JSON output
- keep snapshots stable for CLI tests

This can start small and be introduced once `list --json` or `merge --json`
exists.

## Domain Model

The central object should be a `Plan`.

```go
type Plan struct {
    Roots      []*stackedpr.Node
    Pulls      []PullStatus
    Actions    []Action
    Warnings   []SelectionWarning
    HeadSHAs   map[string]string
}
```

`PullStatus` explains why a PR is or is not actionable:

```go
type PullStatus struct {
    PR          gitobj.PullRequest
    OriginalBase *gitobj.PullRequest
    State       PullState
    NewBase     string
    Upstream    string
    Reason      Reason
}
```

Suggested enum names:

```go
type PullState string

const (
    PullStateClean       PullState = "clean"
    PullStateBroken      PullState = "broken"
    PullStateUpdateable  PullState = "updateable"
)
```

Reasons are important for TUI and JSON:

```go
type Reason string

const (
    ReasonMergedBase       Reason = "merged_base"
    ReasonParentDiverged   Reason = "parent_diverged"
    ReasonMergedAncestor   Reason = "merged_ancestor"
    ReasonRebaseAll        Reason = "rebase_all"
)
```

Actions should be explicit and serializable. For M1, keep them high-level:

```go
type Action struct {
    ID       string
    PR       gitobj.PullRequest
    Kind     ActionKind
    NewBase  string
    Upstream string
    DependsOn []string
}

type ActionKind string

const (
    ActionRepairPR     ActionKind = "repair_pr"
    ActionUpdateBranch ActionKind = "update_branch"
)
```

Execution can expand `repair_pr` into lower-level steps:

- create worktree
- rebase
- push
- update base
- cleanup

Low-level steps can become a public JSON shape later, but they should not be the
first migration boundary. Starting with high-level actions keeps the new planner
close to the current behavior and avoids encoding implementation details into
the first CLI contract.

## Plan Selection

Planning and selection should be separate.

The planner should analyze the full repository snapshot and produce a complete
`Plan`. CLI flags and TUI choices should then select a smaller plan for display
or execution.

```go
type Selection struct {
    Items []SelectionItem
}

type SelectionItem struct {
    PRNumber int
    Mode     SelectionMode
}

type SelectionMode string

const (
    SelectNode    SelectionMode = "node"
    SelectSubtree SelectionMode = "subtree"
    SelectStack   SelectionMode = "stack"
)

func (p *Plan) Select(selection Selection) (*Plan, error)
```

Selection rules:

- empty selection selects every action
- `SelectNode` selects actions targeting exactly that PR
- `SelectSubtree` selects actions targeting that PR and descendants
- `SelectStack` selects all actions in the root stack containing that PR
- repeated and mixed selectors are a union
- duplicate action IDs are removed
- selected actions preserve the original planner order
- dependency actions are not automatically included

If a selected action depends on an unselected action, selection should attach a
structured warning to the selected `Plan`. This keeps CLI and TUI behavior close
to Git's explicit branch operations: gh-domino helps the user select GitHub PR
branches, but it does not silently repair other branches.

## App Ports

The app layer should define narrow ports before it knows about gitkit concrete
clients:

```go
type RepositoryStore interface {
    Fetch(ctx context.Context, remote string) error
    OpenPullRequests(ctx context.Context, author string) ([]gitobj.PullRequest, error)
    MergedPullRequests(ctx context.Context, author string, limit int) ([]gitobj.PullRequest, error)
    RefSHA(ctx context.Context, ref string) (string, error)
    DefaultBranch(ctx context.Context) (string, error)
    MergeBase(ctx context.Context, a, b string) (string, error)
    IsAncestor(ctx context.Context, ancestor, descendant string) (bool, error)
}

type Executor interface {
    RepairPR(ctx context.Context, action Action) error
    UpdateBranch(ctx context.Context, action Action) error
}
```

These ports are intentionally close to gh-domino's use cases, not generic GitHub
or Git clients. The gitkit-backed implementation can live in `internal/app` or
`internal/app/gitkitstore` once it grows.

Current implementation state:

- `internal/app.LegacyStore` implements `RepositoryStore` with the existing
  `git` package.
- `internal/cli` builds read-only plans through `LegacyStore`.
- mutating `merge --yes` should stay blocked until a new `app.Executor` exists.

This gives `list`, `plan`, and `merge --dry-run` a new contract without
preserving the old mutating flow as a second execution path.

## Planning Flow

The loader gathers raw state:

1. `git fetch origin`
2. `gh pr list --author @me`
3. `gh pr list --author @me --state merged --limit 30`
4. `git rev-parse origin/<head>` for every open PR
5. build the dependency tree

The planner then walks the tree in DFS order and computes:

- whether each PR is broken
- which new base should be used
- which upstream commit is needed for squash-merge repair
- whether a clean PR should get an update-branch action under `--all`

Important change from current behavior: dry-run should not mutate `HeadSHAs`.
Instead, the planner should keep an in-memory `projectedHeadSHAs` map that is
local to planning.

## Execution Flow

Execution consumes selected actions from a plan. It should execute only the
selected actions. Warnings about unselected dependencies are advisory and must
not become implicit work.

For a broken PR:

1. create worktree if needed
2. rebase branch
3. abort rebase on conflict
4. push with force-with-lease
5. update PR base when changed
6. refresh projected branch SHA
7. cleanup worktree

For an updateable PR:

1. call `gh pr update-branch --rebase <number>`

The executor returns structured results:

```go
type RunResult struct {
    Actions []ActionResult
}

type ActionResult struct {
    ActionID string
    Status   ActionStatus
    Error    string
}
```

TUI and CLI can render the same result differently.

## Execution Parallelism

Execution should be parallelized inside one gh-domino process, not by asking
users to run multiple processes.

Internal execution has the necessary shared context:

- one repository snapshot
- one selected action DAG
- dependency ordering between actions
- coordinated worktree allocation
- one result stream

External parallel execution would duplicate loading and planning, and it could
race on local refs, worktrees, rebases, or force pushes.

Executor shape:

```go
type ExecuteOptions struct {
    Parallel    int
    WorktreeDir string
}
```

The executor should build a small DAG from `Action.DependsOn`:

- selected actions with selected dependencies wait
- selected actions in the same stack naturally serialize
- unselected dependencies remain warnings and do not execute
- independent stacks can run concurrently up to `Parallel`
- failures mark dependent actions as skipped
- rebase conflict produces a specific result status

Start with `Parallel: 1` for deterministic CLI behavior. The scheduler can be
introduced before changing the default.

## gitkit Integration

Use `github.com/134130/gitkit` as the process boundary.

App wiring should look like this:

```go
runner := gitcmd.NewRunner()
git := gitrepo.New(runner, gitrepo.WithDir(workDir))
gh := ghcli.New(runner, ghcli.WithDir(workDir))
prs := ghpr.New(gh, git)
```

The old `git` package should be treated as migration source code only. New v3
code should not add new call sites to it.

Migration target:

- no package-level `git.CommandRunner`
- no `git.CommandModifier`
- no direct `*exec.Cmd` exposure outside gitkit
- command output streaming is configured once through injected services

### M3 gitkit Store Design

The first gitkit migration should replace `LegacyStore`, not the executor.

Target package:

```text
internal/app/gitkitstore
```

Proposed type:

```go
type Store struct {
    git    gitrepo.Client
    gh     ghcli.Client
    remote string
}

func New(r gitcmd.Runner, opts ...Option) Store
```

Responsibilities:

- implement `app.RepositoryStore`
- preserve current `gh pr list` JSON fields
- parse PR JSON into existing `gitobj.PullRequest`
- call `gitrepo.Client` for `Fetch`, `RefSHA`, `DefaultBranch`, `MergeBase`,
  and `IsAncestor`
- call `ghcli.Client` for open and merged PR lookup

Do not migrate `RepairPR` execution in the same patch. Read-only store behavior
is easier to validate and gives `list`/`plan` a clean command boundary first.

### YAML Replay Migration

The existing YAML replay tests are built around `git.Runner` and command strings.
For gitkit, add a new fake runner that implements `gitcmd.Runner` and consumes
the same YAML shape:

```yaml
- command: git fetch origin
  stdout: ""
  stderr: ""
  exitCode: 0
```

The fake runner should be introduced for the new store and executor surfaces.
Avoid adding more test coverage around the old `domino.Run` path.

### gitkit Migration Order

1. Add `github.com/134130/gitkit` dependency with a local replace while the
   library is still developed in `../gitkit`.
2. Add `internal/app/gitkitstore.Store`.
3. Add `gitcmd` YAML replay runner for tests.
4. Switch `internal/cli buildPlan` from `LegacyStore` to `gitkitstore.Store`.
5. Delete the old runner adapter once read-only commands are on gitkit.
6. Only then design and add `app.Executor`.

## TUI Design

Recommended screens:

1. Loading
2. Plan
3. Confirm
4. Running
5. Result

The Plan screen is the core:

- tree/table hybrid layout
- left side: checkbox, status, PR number, title
- right side: base/head and action summary
- filter tabs: all, broken, selected
- footer: compact key hints

The TUI should use stable row heights and truncate long titles. Avoid relying on
ANSI width from already-styled substrings for cursor row backgrounds; keep row
rendering data-oriented first, then style at the end.

## CLI Output Design

Human output should be terse and stable:

```text
Pull Requests
└─ #52 bar (stack-1 <- stack-2) [broken: merged_base -> main]
   └─ #53 baz (stack-2 <- stack-3) [broken: parent_diverged]

Actions
  rebase #52 stack-2 onto main
  update-base #52 to main
  rebase #53 stack-3 onto stack-2
```

JSON output should mirror `Plan` and `RunResult`, not terminal strings.

## Integration Tests

Keep three layers:

1. Domain tests: pure planner tests with PR fixtures.
2. Command replay tests: fake `gitcmd.Runner` tests for store/executor ports.
3. End-to-end tests: local Git fixture plus GitHub API emulator.

`vercel-labs/emulate` provides a stateful local GitHub emulator that can be
started with only the GitHub service, and it supports seed files and
programmatic startup. Design assumptions should be validated in a spike before
the test suite depends on it.

The E2E harness should:

- create a bare remote Git repository
- clone a working repository
- create branch stacks and commits locally
- seed equivalent GitHub PR state in the emulator
- run `gh domino list --json`
- run `gh domino merge --dry-run --json`
- later run `gh domino merge --yes`
- assert local Git refs and emulated PR state

Risk: `gh` itself may not support redirecting every API path to the emulator in
the way we need. If that becomes too brittle, the app layer should use `ghcli`
only behind an interface so tests can replace the GitHub API client while local
Git remains real.

## Migration Milestones

### M1: Planning Types

- introduce `internal/app.Plan`
- introduce `internal/app.Action`
- add planner tests around PR/stack scenarios
- do not keep a second legacy execution path

### M2: CLI Routing

- add `internal/cli`
- support `list`, `merge`, and default `tui`
- implement v3 flags only
- freeze read-only output snapshots

### M3: gitkit Boundary

- add local module dependency on gitkit during development
- introduce app service dependencies
- replace global runner in new code
- move YAML runner to `gitcmd.Runner`

### M4: TUI Rewrite

- build the new TUI against `Plan`
- snapshot key view states
- remove the old selection model once parity is reached

### M5: Emulator E2E

- add `test/e2e`
- start GitHub emulator in tests
- add local Git repository fixture
- validate `list` and dry-run first
- add mutating execution tests after the API spike

### M6: Remove Legacy

- remove old `git` package after gitkit coverage is complete
- remove package-level mutable output
- remove old headless/TUI branching
- update README for 3.0.0
